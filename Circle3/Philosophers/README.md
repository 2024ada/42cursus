## 무엇을 만들었는가

여러 철학자가 포크를 공유하며 식사·수면·생각을 반복하는 시뮬레이션입니다. 두 포크를 확보해야 식사할 수 있고, 정해진 시간 안에 식사하지 못하면 사망합니다. 공유 자원에 대한 접근과 종료 조건을 관리하는 동시 실행 문제를 다룹니다.

**사용 기술:** C, POSIX Threads, 뮤텍스, `fork`, named semaphore, `waitpid`, 신호, `gettimeofday`.

## 과제에서 요구한 범위

[Subject v11.2](en.subject.pdf)은 필수와 보너스에서 실행 모델을 다르게 지정합니다.

| 구분 | 명세의 요구사항 |
| :--- | :--- |
| 필수 | 철학자마다 스레드를 만들고 포크를 뮤텍스로 보호 |
| 보너스 | 철학자마다 프로세스를 만들고 포크 수를 세마포어로 관리 |
| 공통 | 식사·수면·사망 시간 관리, 상태 로그, 선택적인 최소 식사 횟수 조건 |

생존 감시와 출력 동기화는 두 구현 모두에 필요한 동작입니다. 보너스에서는 **식사 진입 게이트와 프로세스별 감시 스레드**를 두어 이를 구성했습니다.

## 두 가지 구현

| 구분 | 기본 · `philo` | 보너스 · `philo_bonus` |
| :--- | :--- | :--- |
| 실행 단위 | 철학자별 스레드 | 철학자별 자식 프로세스 |
| 포크 표현 | 공유 상태 배열과 포크별 뮤텍스 | 개수를 관리하는 공용 세마포어 |
| 생존 감시 | 실행·대기 중 자신의 생존 시간 확인 | 각 프로세스의 별도 감시 스레드 |
| 로그 | 로그·종료 상태 뮤텍스 | 로그·출력 잠금 세마포어 |
| 식사 진입 | 포크 상태 확인 후 획득 시도 | 게이트로 동시 획득 시도 수 제한 |
| 종료 | 종료 플래그와 스레드 회수 | 자식 종료 상태 확인·다른 자식 종료·회수 |

## 구현에서 주목할 부분

### 실행 모델에 맞춘 자원 관리

[기본 시뮬레이션](philo/philo_sim.c)은 스레드가 공유하는 포크 상태를 사용합니다. [뮤텍스 유틸리티](philo/philo_mtx.c)로 상태 읽기와 쓰기를 감싸고, [로그 함수](philo/philo_msg.c)는 출력과 종료 상태를 함께 확인합니다.

보너스는 프로세스 간 공유 자원을 [named semaphore](philo_bonus/philo_sem_bonus.c)로 다룹니다. [식사 진입 게이트](philo_bonus/philo_sim_bonus.c)는 동시에 두 포크를 얻으려는 프로세스를 `⌊N/2⌋`개로 제한합니다.

### 생존 감시와 대기 처리

[기본 시간 처리](philo/philo_time.c)는 짧게 나누어 대기하며 생존 조건을 확인합니다. 보너스에서는 [감시 스레드](philo_bonus/philo_check_bonus.c)가 마지막 식사 시각과 현재 시각을 비교합니다.

### 종료 사유에 따른 정리

사망 또는 선택한 최소 식사 횟수 조건으로 시뮬레이션을 종료합니다. 보너스 [부모 프로세스](philo_bonus/philo_let_bonus.c)는 자식의 종료 코드를 확인하고, 사망 시 다른 자식들을 종료한 뒤 회수합니다. 세마포어의 닫기와 이름 제거도 별도 함수로 관리합니다.

## 빌드와 실행

각 구현 디렉터리에 Makefile이 있습니다.

```sh
# Philosophers 디렉터리에서
make -C philo
./philo/philo 5 800 200 200 5

make -C philo_bonus
./philo_bonus/philo_bonus 5 800 200 200 5
```

인자는 아래 순서이며 시간 단위는 밀리초입니다.

```text
철학자 수  사망 제한 시간  식사 시간  수면 시간  [최소 식사 횟수]
```

마지막 인자를 생략하면 횟수 기준의 종료 조건을 사용하지 않습니다. 로그는 `경과 시간 철학자 번호 상태` 형태로 출력됩니다.

각 하위 디렉터리에서 `make clean`, `make fclean`, `make re`를 사용할 수 있습니다.

<details>
<summary>동기화 구현의 현재 범위</summary>

기본 구현은 포크 상태의 확인과 갱신을 각각 잠금으로 감쌉니다. 두 작업을 하나의 임계 구역으로 묶는 원자적 획득 처리는 개선할 항목입니다. 시작 지연은 경합을 완화하는 방식이며 기아 방지까지 보장하지는 않습니다.

생존 감시는 짧은 주기의 확인과 운영체제 스케줄링에 의존합니다. 엄격한 실시간 응답이나 모든 실행 순서에서의 무교착을 보장하는 구현으로 설명하지 않습니다.
